# UX Findings: Open Mic Explorer usability audit

Date: 2026-08-06. Audited at commit `3341da7` (main). Method: full read of the route tree, the two core flows traced file by file, four parallel code sweeps (auth and permissions, forms and accessibility, the signup state machine in the migrations, navigation and store readiness). Docs were treated as claims and verified against code. Every finding carries a file and line citation. Baseline suite at audit time: typecheck clean, lint clean, 455 Jest tests passing, `npm run format:check` FAILING on 24 pre-existing files (see finding R1).

Severity definitions:

- Blocker: user cannot complete the core job, loses their slot, is misinformed about whether they are on a list, or the app fails review
- High: measurable drop off or a predictable support message
- Medium: friction or inconsistency a regular user notices
- Low: polish

Tab bar: five tabs, text labels, all destinations, none hidden or disabled by role or state (`src/app/(tabs)/_layout.tsx:21-59`). "Add a mic" is a screen-level button on My Mics (`src/app/(tabs)/producer.tsx:129`), not a tab. This matches the rubric as-is.

### 1.2 Tap counts, cold open to task complete

Performer, signed in, home area set (the returning-user case):

1. Cold open lands on Discover, list view, soonest-first, centered on home area, own disciplines pre-selected (`src/app/(tabs)/index.tsx:33-97`)
2. Tap a mic card (tap 1)
3. Tap "Sign me up" in the sticky footer (tap 2, `src/app/mic/[id].tsx:446-454`, `src/features/signups/cta.ts`)

Total: 2 taps, no typing, no modals. Meets the one-screen-one-confirm target.

Performer with an account but signed out: 5 taps plus typing, and the flow loses the mic. Card (1), "Sign in to get on the list" (2), sign-in form submit (3), the auth gate then replaces the stack with the Discover tab (`src/app/_layout.tsx:103-105`), so the user must re-find the mic (4) and tap "Sign me up" (5). Finding A3.

Brand-new user: roughly 8 taps, 6 to 7 text fields, and possibly an app exit. Browse (0), card (1), footer CTA (2) lands on sign-in, not sign-up, so "New here? Create an account" (3), email and password then "Create account" (4), then, if email confirmation is enabled on the hosted project, a terminal "Check your email" screen whose link points at a dead loopback URL (finding A4), then sign in again by hand, EULA accept (5), onboarding with stage name, city and state or ZIP, birth year, then "Finish setup" (6), landing on Discover with the original mic lost, re-find it (7), "Sign me up" (8). Findings A2, A3, A4.

Producer, signed in with the producer role: My Mics tab (1), "Add a mic" (2), one form screen (name, discipline chip, schedule chips, time selects, method select, venue search and pick; roughly 8 to 12 inputs for a typical listing), "Create listing" (final tap), landing directly on the Manage screen for the new mic. The form is one screen with inline validation on text fields and a live plain-English schedule preview. This flow is in good shape.

Producer opening tonight's list: My Mics (1), "Open tonight's list" on the card (2). Excellent.

### 1.3 Signup states: database versus UI vocabulary

`signup_status` enum, defined once and never altered (`supabase/migrations/20260728000100_extensions_and_types.sql:11`): `requested`, `confirmed`, `waitlisted`, `drawn`, `performed`, `no_show`. Withdrawal is a row DELETE, not a status (`src/features/signups/queries.ts:186-194`). On deck is an orthogonal timestamp (`on_deck_at`). Occurrence status adds `scheduled`, `cancelled`, `moved`, `completed`; `moved` and `completed` are never written or rendered anywhere. Walk-in guests are signups with `guest_name` and no `performer_id`. Attendance plans are a separate table with no status at all.

There are two label maps both exported as `STATUS_LABELS`: `src/features/signups/components/signup-card.tsx:25-32` (performer voice) and `src/features/signups/labels.ts:11-20` (roster voice, aliased). They disagree, and the two performer-facing surfaces (signup card, Going tab) use opposite maps.

| DB status    | Signup card and footer                      | Going tab                    | Profile "My nights"                               | Producer roster                      | Push copy                                |
| ------------ | ------------------------------------------- | ---------------------------- | ------------------------------------------------- | ------------------------------------ | ---------------------------------------- |
| `requested`  | "In the draw"                               | "In the draw"                | "In the draw"                                     | "In the draw"                        | none exists (finding D2)                 |
| `confirmed`  | "On the list · Slot N in the running order" | "On the list, slot N"        | "On the list"; past nights read "Was on the list" | "On the list"                        | "You are on the list. You are number N." |
| `waitlisted` | "Waitlisted"                                | "Waitlisted"                 | "Waitlisted"                                      | "Waitlisted"                         | "You are on the waitlist."               |
| `drawn`      | "You are in: drawn for a spot"              | "Drawn: on the list, slot N" | "You are in: drawn for a spot"                    | "Drawn: on the list"                 | "You were drawn! You are on the list."   |
| `performed`  | "Performed"                                 | "Performed"                  | "Performed"                                       | "Performed" ("done" on Live)         | "Marked as performed. Nice set."         |
| `no_show`    | "Marked no-show"                            | "Marked no-show"             | "Marked no-show"                                  | "Marked no-show" ("no-show" on Live) | "You were marked as a no-show."          |

`drawn` has four distinct user-facing strings. Slot phrasing drifts across five variants (" · Slot N in the running order", " · Slot N", ", slot N", "(Slot N)", "You are number N"). "Full" copy has three variants. No email copy exists anywhere; notifications are push only. Full citations under finding D1.

## 3. Annotated flow walkthroughs

### 3.1 Performer signup, cold open to on the list

Screens in order, friction marked inline.

1. Cold open, Discover (`src/app/(tabs)/index.tsx`). List view, centered on home area (or labeled Seattle default with an explanatory note for guests), soonest-first, own disciplines pre-seeded, offline banner, pull-to-refresh. Cards carry discipline accents, venue, distance in miles, recurrence plus concrete next date, method, cost, freshness, spots left. FRICTION E5: no date grouping; days interleave. Solid otherwise.
2. Tap a card, mic detail (`src/app/mic/[id].tsx`). Poster, title, share, star, freshness plus stewardship, schedule card with calendar button, signup card, plan toggle, method card with facts, venue card with directions. The one primary action is duplicated: inline card plus sticky footer. FRICTION C3: signup close time never shown; set length, cost, age restriction live in cards below the signup card. FRICTION C4: card and footer buttons are independent mutations. FRICTION E7: header is blank until data lands.
3. Tap "Sign me up" (footer). Signed-in performer: insert runs, haptic fires, card re-renders "On the list · Slot N in the running order". FRICTION D2: nothing pushed, no toast; backgrounding the app leaves no confirmation in hand. FRICTION C5: under contention the confirmation can be a lie (capacity exceeded, duplicated slot numbers). Lottery night: "Put my name in the draw", lands on "In the draw". FRICTION D6: the draw's timing and the not-drawn outcome were never stated before committing.
4. Signed out at step 3: footer reads "Sign in to get on the list", tap lands on the password-first sign-in screen (FRICTION A2), and after auth the gate replaces the stack with Discover, losing the mic (FRICTION A3, blocker for the under-a-minute goal). Brand-new users additionally risk the email-confirmation dead end (FRICTION A4) and then walk the EULA and onboarding gates, which are short (one tap plus five fields) but land on Discover, not the mic.
5. After: the withdraw path is exemplary (two taps, honest copy, undo). The wait between signup and showtime is silent (FRICTION D3): no reminder unless the mic was separately favorited, and that reminder can fire in the middle of the night.

### 3.2 Producer listing creation and running the night

1. My Mics tab (`src/app/(tabs)/producer.tsx`). Guest: benefit prompt. Signed-in non-producer: one-tap "Become a producer" (no re-onboarding). Producer: list of own mics with freshness, next night, signup count, one-tap "Confirm accurate", and "Open tonight's list" surfacing on day-of. Strong screen.
2. "Add a mic" (`src/app/producer/new.tsx`, `series-form.tsx`). One screen: name, discipline chips, schedule chips with live plain-English preview, hour and minute selects, timezone chips auto-set from the venue pin, method select with per-option explanations, signup-opens select, cost, set length, spots, notes, venue search or new-venue block with address-to-pin geocoding. Inline blur validation on text fields, chip requirements at submit, discard guard on back. FRICTION (minor): chip-level errors (discipline, schedule, venue) surface only at the bottom on submit; venue search has no empty state ("no venues match") when results are empty; a new venue collects no age restriction or accessibility facts, so the listing renders without them (the fields exist on the venues table).
3. Create lands on Manage (`producer/[id].tsx`): edit with this-night versus all-future semantics, confirm accurate, pause with warning, cancel a night with reason, posters, lineup credits, analytics. FRICTION E7: loading branch is headerless.
4. Night roster (`producer/night/[occurrenceId].tsx`). Composed title (mic plus night), who-is-coming counts, draw box with visible shuffle and closed-draw explanation once the show starts, running order with prominent slot numbers, 44pt icon actions (on deck, move, performed, no-show, report), undo on performed and no-show, walk-in add, waitlist promote, confirmations for no-show and re-draw. This screen has clearly been worked and it shows. FRICTION C7: nothing tells the host a slot freed when someone withdraws; the list just shrinks. FRICTION F8: no pull-to-refresh (realtime covers most of it).
5. Live (`producer/live/[occurrenceId].tsx`). FRICTION E7: title is a bare "Live". FRICTION G2 and G3: fixed 22px slot column and sub-AA struck names for no-shows, on the screen used in the darkest room.
